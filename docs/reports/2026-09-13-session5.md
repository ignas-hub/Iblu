## What exists now that did not

**The mission says what Iblu may read (2026-09-13).** The "personal
infrastructure only" principle drew the line in the wrong place — it read as
"Iblu may not look at company systems", when what Ignas meant was "Iblu does not
*host* anything company-owned". Read access to any venture's systems, including
company code, is now explicitly in scope; running company workloads and holding
write credentials to them explicitly is not. GoStellar joined the venture list.
Re-seeded: `mission_sha=e8349a29`, `mission_stale=false`.

**The Gain principle is now a rule with teeth.** "Progress is measured backward
against the baseline, never against the ideal, a goal, a competitor or another
person. Gains come first in every Iblu output; the day is shown as a done list,
never a to-do list." Plus the counting cadence: 24 h, 7 d, 30 d, 90 d, 12 m,
measured backward from the 2026-09-13 baselines, with an initiative reaching
`autonomous` as the largest gain.

**`gmail_reply` asks before it sends.** A threaded reply lands in someone's
inbox exactly as a new mail does, and the thread makes it *more* likely to be
read. Three tools now ask — `gmail_send_email`, `chat_send_message`,
`gmail_reply` — and only those three.

**GoStellar is a venture with a priority and a baseline.** `ventures` has 7
rows. The yearly priority was written through the `context_log` code path, not
by hand, so it carries the same shape as the other six. The GoStellar baseline
(`c1fb0cad`) had been written with `venture=NULL` because the venture did not
exist yet; it now points at `gostellar`. That was the one permitted raw
`UPDATE`.

**Priorities and baselines are visible everywhere, with no new tool.**
`store/governance.py` holds `current_priorities()`, `current_baselines()`,
`gain_rules()` and `as_prompt_block()` — one implementation, used by every
consumer. `get_context` returns `mission → mission_sha → mission_stale →
priorities → baselines → gain_rules → brief → summary`, and its docstring now
tells the reader to measure backward from the baselines and judge everything
else against the priorities. Verified live: 7 priorities, 8 baselines, gain
rules present, mission not stale.

**Stages and the initiative registry exist (migration 007).** Eight stages from
`research` to `autonomous`; 28 projects seeded across all seven ventures, every
one `inferred` and dated 2026-09-13, because Ignas has not confirmed any of them
yet. `project_stage_history` records every move. A project cannot enter
`autonomous` while `done_means` is NULL — enforced in code, since that is the
stage he actually fails at. `venture_hints` resolves project names from the
registry's aliases, so signals attach to projects from the first tick.

**A goal written as a Gap now says so.** `context_log` returns a `gap_warning`
on a decision or preference containing a superlative, a comparison to another
company, a race, an obligation, or a distance from an ideal — and on a
`priority` that names no observable end state. It never blocks the write. A
warning that blocks is a grader, and Iblu measures.

## What the repo contradicted

- **Migration numbering.** The brief assumed 003 was the last migration and
  called stages/projects "004". The repo was already at 006. Stages and
  projects became **007**. The brief's "migration 005 — blocks" was likewise
  already built (005) and extended (006).
- **`gostellar` was not seedable by migration.** Migration 001 seeds the six
  original ventures, and `tests/test_migrations.py` asserted that set exactly.
  The mission says adding a venture is one row, not a migration — so the
  assertion became a subset check, with a comment saying why. Work types stayed
  an equality: a new work type would change the meaning of every answer already
  given.
- **Three project aliases were deliberately left out** — `opera` (BLT's
  `opera-desktop` vs Choco's `choco-opera`), `alexan` and `emory` (two
  initiatives each, same person). A wrong alias silently mis-attributes work,
  which is worse than leaving a name unregistered.
